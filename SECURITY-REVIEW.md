# Security Review

## Confirmed Issues Fixed

- Page bridge messages now use a per-page token, strict type allowlists, origin/source checks, JSON size limits, and payload schema validation.
- Markdown link insertion now permits only `https:`, `http:`, and `mailto:` URLs and rejects unsafe or obfuscated schemes.
- Storage reads now validate volume and recent emoji values before use.
- Prototype-sensitive stored volume data is copied into `Object.create(null)`.
- Debug logging no longer reads composer `innerHTML`.
- The local participant no longer receives a volume slider. Detection (`isLocalCard()` in `src/content/index.js`) checks, in order of trust: (1) an explicit `data-local="true"` / `data-local-participant="true"` marker on the card itself; (2) if that marker is on a different card than the one being checked, a stable `data-call-participant-id` / `data-participant-id` / `data-participant-identity` shared between the marker and the card; (3) as a last resort, display-name equality against the resolved local username (`localUserName()`). Every animation-frame scan re-runs this check per card (`addSlider()` removes any slider a card already has as soon as it's recognized as local), so a card that starts unresolved, gets a slider by mistake, and is later confirmed local has that slider removed rather than left in place. This also covers cards recreated across reconnects/navigation, since detection is attribute- and id-based rather than tied to a specific DOM node.
- **Confirmed against a live call** that branches (1) and (2) above are currently dead code on at least one real Chatto deployment: no participant card carries `data-local`, `data-local-participant`, or any participant-id attribute. Detection therefore runs on branch (3) alone in practice.
- **Actual root cause of the first name-comparison fix still failing live:** `localUserName()` read the wrong DOM node, not a fundamentally decorated name. `[data-testid="current-user-identity-text"]` (the account panel shown at the bottom of the channel sidebar, reused for the in-call "you are" label) nests markup like `<span>` (name row) → `<span>{plain name}</span>` plus an optional sibling `<span title="{status}">` carrying a custom status emoji, one level deeper than the name. The original strategy read `el.firstElementChild.textContent`, which is the whole name-row span — so it concatenated the status emoji's text onto the name (observed live as `"Loading 🐑"` vs. the card's plain `"Loading"`). This was a real DOM-traversal bug, not a load-order race or an inherent decoration on the name itself.
- Fixed by adding a `testid-name-span` strategy to `localUserName()` that reads `el.firstElementChild.firstElementChild` — the innermost span holding only the plain name — ahead of the old (now demoted, kept as fallback) strategies. `isLocalCard()` also still applies `stripTrailingDecoration()` (strips a trailing run of whitespace/pictographic characters) as a second line of defense for the coarser fallback strategies or any future DOM shape Chatto ships. Covered by `test/local-card-detection.test.mjs`, which reproduces the exact nested-span/status-span structure rather than a flattened stand-in.

## New Feature: GIF Picker

- Adds a GIF button beside the emoji button that searches Giphy and, on pick, uploads the result as a real file rather than pasting its URL — a bare GIF link was confirmed (by hand) to sit static in Chatto rather than animate, while an uploaded `.gif` file plays normally.
- **API key handling:** Giphy issues one API key per *app*, not per end user (unlike Tenor, whose public developer program was found to be closed to new applicants as of Jan 2026 — the reason this feature targets Giphy rather than Tenor). Collecting a per-installer key was therefore never the right model here; the key is instead the maintainer's own, injected into `src/background.js` at build time from a `GIPHY_API_KEY` environment variable (see `scripts/build.mjs`). `src/background.js` as committed to the repository — what anyone browsing GitHub sees — contains only the literal placeholder `__GIPHY_API_KEY__`; the real key exists only in the gitignored `dist/` and `artifacts/` build output on the maintainer's machine. Building without the environment variable set produces a working extension with GIF search cleanly disabled (`no-key` error path), rather than failing the whole build.
- **This does not make the key un-extractable, and isn't meant to.** Anyone who installs the finished, built extension can still find the real key by inspecting their own local copy — that is an inherent property of any client-side app key, and is how Giphy expects its API to be embedded in client applications (its own rate limiting is designed around this). What the build-time injection actually achieves is narrower and specific: the key never appears in the git history or the public GitHub source, so it can't be found by browsing the repository, scraped by automated secret-scanning of the source, or reused by someone who never installed the extension at all.
- **Why a background service worker exists at all** (this extension previously had none): a content script's `fetch()` runs inside the page's own JavaScript realm and is bound by the page's CSP, which this extension does not control and should not need to work around. All Giphy requests (search and fetching the actual GIF bytes) are made from `src/background.js` instead, in the extension's own privileged context, scoped by the `https://api.giphy.com/*` and `https://*.giphy.com/*` entries newly added to `host_permissions`. This is the first host permission this extension has ever requested beyond Chatto's own origins, and the first time any user-generated content (the GIF search query) leaves the extension to a third party other than Chatto.
- **Fetch relay is domain-locked, not a general proxy:** `background.js`'s `gif-fetch` handler (`isSafeGiphyUrl()`) only fetches URLs whose scheme is `https:` and whose host ends in `.giphy.com` — the content script cannot use it to fetch arbitrary attacker-controlled URLs even if a hostile page script could somehow reach it (it cannot: `sendBg()` messages originate only from the extension's own picker UI, never from data the page controls).
- **Response validation:** fetched GIF bytes are capped at 15 MB and rejected unless the response's `Content-Type` is `image/gif`, before ever being handed to the content script or turned into a `File`.
- **Search query handling:** the query string is length-capped (200 chars) and passed to Giphy via `URLSearchParams` (proper encoding, no string concatenation into the request URL).
- **Favorites** are a new locally-stored preference (`gifFavorites` in `chrome.storage.local`, alongside the existing `volumes`/`recents` keys), validated on read the same way those already are: `cleanGifFavorites()` caps the list at 200 entries, dedupes by id, and — since favorited GIFs are rendered as `<img src>` directly from stored data without passing through `background.js`'s fetch relay the way inserting one does — `isGiphyMediaUrl()` restricts both `url` and `previewUrl` to `https://*.giphy.com` before they are ever used as an image source. An `<img src>` can't execute script even if this were bypassed, so this is defense-in-depth rather than a response to a demonstrated exploit path.

## New Feature: Screen-Share Pop-Out (Picture-in-Picture)

- Adds a button to each screen-share card's own toolbar (`[data-testid="call-media-actions"]`, alongside Chatto's own Fullscreen/Mute buttons) that calls the standard `HTMLVideoElement.requestPictureInPicture()` Web API on that card's `<video>`. Confirmed working live before implementation, per this project's established practice of verifying live behavior rather than guessing.
- No new permissions, no new network access, no new stored data — this is a client-side call into a standard browser API operating on a `<video>` element Chatto itself already rendered. `ensurePipButtons()` no-ops entirely if `document.pictureInPictureEnabled` is false, so it's inert on any browser/build without PiP support rather than throwing.
- The button reuses Chatto's own Tailwind utility classes for that toolbar's buttons verbatim (the same classes Chatto's own Fullscreen/Mute buttons in the identical toolbar already use) rather than this extension's usual `.ce-*` styling, so it visually matches Chatto's native controls. The icon is self-drawn in this codebase's existing stroke-icon convention, not loaded through Chatto's own Iconify classes — those appear to be generated at Chatto's own build time for icons Chatto's build actually references, so a class this extension injects at runtime for an icon Chatto never used would very likely resolve to no visual glyph at all.
- **Known, unfixable platform limitation:** the popped-out window's "stay on top of every window" behavior is confirmed reliable on Windows, macOS, and Linux/X11, but is inconsistent on Linux/Wayland (any compositor, not specific to one desktop environment) — Wayland's design deliberately prevents a client from forcing itself above other windows. This is a browser-and-compositor matter entirely outside what a content script can influence; documented here rather than "fixed," since there is nothing in this extension's control to fix.

## New Feature: Local Nicknames

- Adds a "Rename" button to Chatto's own user-profile popover (the one with "Send Message" / "Ban from room"), letting a user set a **purely local, visual** nickname for someone. This does not call any Chatto API and does not rename anyone server-side — Chatto, and everyone else, still sees the person's real name. Clicking it opens an inline text field directly under the button (inside Chatto's own popover, not a native `window.prompt()`), with a checkmark button to confirm; its placeholder says "only visible to you" so nobody mistakes this for an actual rename.
- **Storage and validation:** nicknames are stored as a `nicknames` object in `chrome.storage.local` (alongside `volumes`/`recents`/`gifFavorites`), keyed by the person's real display name — the same convention, and the same known duplicate-display-name caveat, already documented above for per-participant volume levels. `cleanNicknames()` validates both the key and value through the same `cleanName()` used elsewhere (length-capped, trimmed) and caps the total table at 500 entries.
- **Scope:** the nickname is displayed on call participant cards, message author names (the bold name above a message), the member sidebar list, and the direct-message list — four distinct pieces of Chatto markup, each found and confirmed against real DOM evidence rather than guessed. It deliberately does **not** touch message *content* anywhere: every surface only targets a name-label element (a sidebar row, an author-name button, a card title), never the body of a message, because rewriting text a person actually typed to say something they didn't would misrepresent the conversation — which this extension does not do anywhere else either. The profile popover's own header is also deliberately left showing the real name, since the Rename prompt reads its context from there and swapping it too would make editing a nickname confusing.
- **Fix for a real bug found in testing:** the first version of the hide-and-replace swap copied the *already-hidden* class list onto the replacement label, so both the real name and the nickname ended up hidden — a blank name in the call panel. Fixed by computing the label's classes from a filtered snapshot of the original element's classes (stripping `ce-name-hidden`/`ce-nick-label`) before the hide class is applied, in the shared `swapNameDisplay()` helper all four surfaces now use.
- **Why the swap doesn't touch Chatto's own name element:** `swapNameDisplay()` hides Chatto's own name node with a CSS class (`ce-name-hidden`) and inserts a sibling element carrying the nickname, re-applied every scan, rather than overwriting the real name node's text content directly. Chatto's Svelte rendering could otherwise silently revert an in-place edit the next time that specific element re-renders (e.g. on a speaking-state change); a class toggle plus a separate sibling element survives that. It also means an element's own `textContent` always stays the real name no matter how long it's been hidden, which the message-author and DM-list surfaces rely on directly (they have no `title` attribute or testid to read the real name from, unlike the member sidebar's `title="View profile of <name>"` or call cards' `nameOf()`). Every piece of this extension's own internal logic (`nameOf()`, local-user detection, volume storage keys, voice-to-stream matching) continues to read the *real* name — nicknames are a display-only overlay layered on top, never substituted into logic that depends on matching Chatto's actual data.
- **Selector fragility, worth naming directly:** the message-author surface has no `data-testid` or stable attribute to match on at all — it's identified by a specific combination of four Tailwind utility classes (`font-semibold`, `hover:underline`, `leading-none`, `inline-flex`) that happened to be distinctive in the DOM evidence gathered. This is more fragile than this extension's usual `data-testid`-first, multi-strategy cascade approach, and is the most likely of the four new surfaces to silently stop matching if Chatto changes that button's styling. The DM-list surface (`a.sidebar-item` narrowed to ones with a direct-child `span.flex-1.truncate`) carries a small, low-probability edge case: a channel whose name happens to exactly equal a nickname's real-name key would also get relabeled, since nothing distinguishes a channel link from a DM link at that selector's level of precision.

## New Feature: Settings Popup and Feature Toggles

- Adds a toolbar popup (`src/popup.html`/`src/popup.js`, wired via the manifest's `action.default_popup`) letting a user turn each feature off independently: volume sliders, emoji picker, GIF picker, markdown toolbar, screen-share pop-out, and local nicknames. A `settings` object in `chrome.storage.local` records the choices, validated by `cleanSettings()` the same way every other stored value in this extension already is (unknown keys ignored, non-boolean values ignored, always falls back to "on" per feature).
- **What "disabled" actually skips, and what it can't:** turning a feature off skips its setup work entirely on the next page load — its buttons are never built, its DOM never constructed, and for the GIF picker specifically, no network request to Giphy is ever made unless that feature is on. What it cannot skip is the browser loading and parsing this file at all: `src/content/index.js` is declared as one content script in the manifest, so Chromium/Firefox fetch and parse the whole thing regardless of these flags before any of them are even read — splitting into several independently-injected scripts would be a much larger architectural change than this pass, and isn't done here. The real, measurable saving is in avoided *work* (most notably: never building roughly 1,900 emoji buttons' worth of DOM when the emoji picker is off), not avoided *page weight*.
- **Takes effect on the next page load, not live.** Flipping a toggle in the popup only writes to storage; the content script reads `settings` once at startup and never re-reads it. Making a toggle apply instantly would require a teardown path for every feature (remove its buttons, close any open picker, disconnect its listeners) in addition to the setup path that already exists — real work, for a responsiveness win most users switching a feature on/off once won't need. The popup says "reload after changing" rather than implying otherwise.
- **Duplication, by necessity:** `popup.js` keeps its own copy of the feature list and `cleanSettings()`, identical to the ones in `src/content/index.js`. The two files run in different execution contexts (extension popup vs. content script) and this project has no bundler to share a module between them without adding a build dependency the rest of the project deliberately avoids (see `CONTRIBUTING.md`: no runtime dependencies). Keeping both lists in sync by hand is a real maintenance cost worth naming, not something to pretend isn't there.
- **Optimization alongside this:** the three separate `chrome.storage.local.get()` calls this extension made at startup (one each for volumes/recents, nicknames, and GIF favorites) are now one combined read, cutting two redundant storage round-trips regardless of which features are enabled.
- **Export / Import, added to the same popup.** Since nothing this extension stores syncs across browsers or profiles on its own, an Export button downloads volumes/recents/nicknames/GIF favorites/settings as a JSON file, and an Import button reads one back in. Import only checks that the file is valid JSON and copies through the known top-level keys (`volumes`, `recents`, `nicknames`, `gifFavorites`, `settings`) — it does not re-validate the *contents* of each one (that a volume is really a number 0-1, a nickname is under the length cap, and so on). That's intentional, not an oversight: `src/content/index.js` already re-runs everything read from `chrome.storage.local` through `cleanVolumes()`/`cleanNicknames()`/`cleanGifFavorites()`/`cleanSettings()` the next time Chatto's tab loads, regardless of whether that data arrived through normal use or an import. Duplicating that validation inside `popup.js` — a separate execution context, the same duplication concern already noted above for the feature list — would be redundant given that gate already exists downstream.

## New Feature: Perceptual Volume Curve and a Reset-All Button

- **Reported and confirmed:** a volume slider at 50% barely sounded quieter than 100%. The cause is real, not subjective — `main-world.js`'s `apply()` sets the native `HTMLMediaElement.volume` (linear amplitude) directly to the slider's own 0-1 position. Human loudness perception is roughly logarithmic: a 50% amplitude cut is only about a 6dB reduction, well short of the ~10dB reduction that actually reads as "half as loud" to a listener. This is a well-known, generic property of linear volume sliders, not something specific to this codebase.
- **Fix:** `perceptualGain(v) = v * v`, applied only at the boundary where a slider position is turned into the `factor` sent to `main-world.js` (`applyVolumes()` and `setVol()`). What's stored in `chrome.storage.local`, shown as the percentage badge, and used as the slider's own visual position is untouched — a slider at 50% still reads "50%" and sits at the halfway mark; only the actual gain sent for that position changed, from 0.5 to 0.25 (a ~12dB cut), which is far closer to sounding like a genuine "half as loud." This has not been confirmed against real audio yet — the reasoning is grounded in standard audio-taper conventions used for exactly this complaint in other software, but is not itself a measurement of this specific app's audio pipeline.
- **"Reset volumes" button**, added above the participant list (`[data-testid="call-participants-list"]`, a selector already relied on elsewhere as `findCards()`'s own fallback strategy) rather than beside Chatto's own call-controls row, whose exact markup this project has no DOM evidence for. Clears every stored volume back to 100% at once; the existing per-slider double-click reset already covered one person at a time. Reuses `window.__ceReset()`'s underlying logic (clear `volumes`, reapply, repaint) rather than duplicating it.
- **v1.1.1 fix — confirmed live via the extension's own Errors panel: "The AudioContext was not allowed to start."** The speaker-loudness measuring tap (an `AnalyserNode`, never connected to output, used only to help match a stream to a participant card) called `audioCtx()` from inside the periodic level-measuring loop, which lazily constructed a `new AudioContext()` as soon as a live audio stream existed — well before any click or keypress on the page. Chrome logs that warning at *construction* time, not at `resume()` time, so the existing `wake()` handler's `resume().catch(() => {})` never prevented it. Fixed by splitting the read-only `audioCtx()` accessor from a new `ensureAudioCtx()` that is only ever called from inside the `click`/`keydown` listeners themselves — a genuine user gesture. Until the user's first interaction with the page, the level-measuring loop's `tap()` simply returns `null` and that cycle is skipped (a few missed loudness samples right after page load, not a functional loss); volume control itself is unaffected either way, since muting/leveling goes through the separate `HTMLMediaElement.volume` prototype hook, not this analyser.

## New Feature: Emoji Picker Keyboard Shortcut

- `Ctrl+Shift+E` (or `Cmd+Shift+E` on macOS) toggles the emoji picker for whichever composer currently has focus, without touching the mouse. Shift is what keeps this from colliding with the markdown toolbar's own `Ctrl+E` (inline code) — no `FORMATS` entry pairs the `e` key with Shift, so the two handlers can never both match the same keystroke. Only fires while a composer has focus, same restriction as the markdown shortcuts.

## New Feature: "Enable here" for Other Chatto Domains

- Until now the extension only ever activated on the two domains hardcoded into `config/build.json`'s `hostMatches`; any other self-hosted Chatto instance required a manual rebuild. This adds a way to turn it on for a new domain from the popup, without shipping a broad `<all_urls>` permission by default.
- **Manifest changes:** `permissions` gained `activeTab` and `scripting`; a new `optional_host_permissions: ["http://*/*", "https://*/*"]` was added. `optional_host_permissions` grants nothing by itself — it only lists what the extension is *allowed to later ask for*, one origin at a time, via `chrome.permissions.request()`. The extension still ships with host access to nothing beyond Giphy and the two built-in Chatto domains.
- **Flow, in `src/popup.js`:** opening the popup (a user-initiated click on the toolbar icon) silently grants `activeTab` for whatever tab is active — the same permission model Chrome designs for exactly this "click the icon to act on this tab" pattern, with no extra permission prompt of its own. `checkThisSite()` uses that to read the current tab's origin and, if it doesn't already have a stored permission for it, injects a small detection function (`detectChattoInPage`) into the page via `chrome.scripting.executeScript()` to look for Chatto-specific markers (`[data-testid="server-icon"]`, `[data-testid="call-participants-list"]`, `[data-testid="current-user-identity-text"]`, or a `chatto:preferences` localStorage key). Only if one of those is found does the popup show an "Enable here" button.
- **The actual grant is a separate, explicit step:** clicking "Enable here" calls `chrome.permissions.request({origins: [origin + '/*']})`, scoped to that one origin — this triggers the browser's own permission prompt, so the user sees and approves exactly what's being granted, same as any other extension asking for a new site permission. Nothing is granted silently.
- **Persistence:** once granted, `chrome.scripting.registerContentScripts()` dynamically registers the same two content scripts the manifest declares statically for the built-in domains (`main-world.js` in the `MAIN` world at `document_start`, and `emoji-data.js`+`content/index.js`+`styles.css` at `document_idle`), scoped to that origin. This is what makes it "activate automatically on that domain forever" rather than just for the current page load — the registration is stored by the browser and survives navigation and (per Chrome/Firefox's own `scripting` API contract) browser restarts.
- **Detection is a heuristic, not a certainty**, and is stated as such in the popup's own status text ("This looks like a Chatto server") rather than an unconditional claim. It only runs after the user has already taken the deliberate step of opening the popup on that tab; a false positive here would still require the user to separately click "Enable here" and approve a browser permission prompt naming the exact origin before anything is granted, so there is no path from an incorrect detection straight to silent access.
- **Unverified:** `chrome.scripting.registerContentScripts()` with `world: 'MAIN'` requires a reasonably recent Chromium version, and Firefox's own `browser.scripting.registerContentScripts()` support has not been confirmed live in this environment (only that this project's `strict_min_version` postdates when Firefox added the `scripting` API generally). If dynamic registration silently fails on either browser, the permission is still granted (confirmed via `chrome.permissions.contains()` on the next popup open) but the page itself won't be enhanced until this is fixed or the user reloads after a browser update.
- This does not change how the two built-in domains work — their content scripts remain statically declared in the manifest exactly as before.
- **v1.1.1 fix — confirmed live: registration was silently lost when the browser closed the popup.** Some browsers dismiss the extension's own action popup the instant `chrome.permissions.request()` shows its native prompt, which terminates any pending JavaScript in that popup document — including the code that was supposed to call `registerContentScripts()` after the user clicked Allow. This left permission granted but nothing actually registered, forcing a manual "Repair" click every time. Fixed by moving the registration itself into `src/background.js`, listening for `chrome.permissions.onAdded` — the service worker is not tied to the popup's lifetime, so it runs the instant permission lands regardless of what happened to the popup that requested it. `popup.js` keeps its own copy of the same registration attempt as a second, redundant path (and now self-heals automatically rather than requiring a manual click, if it ever finds permission granted but nothing registered), and both are safe to run twice — `registerScriptsFor()`/`registerScriptsForOrigin()` first calls `unregisterContentScripts()` for the same ids before re-registering, rather than erroring on a duplicate id.
- **v1.1.1 addition — on-page reload banner.** Since the settings popup can no longer be relied on to still be open by the time registration finishes, `background.js` now injects a small, dismissible banner directly into the newly enabled tab once registration succeeds ("Chatto Enhancer is enabled here — reload the page to activate it.", with a Reload button), rather than only reporting success inside a popup the user may never see. Chosen over a native OS notification specifically to avoid needing a new `notifications` permission and an icon this extension doesn't otherwise ship. The banner is idempotent (checks for its own element id before inserting) and auto-removes itself after 20 seconds if ignored.

## Defense-In-Depth Improvements

- Chromium and Firefox manifests are generated from a shared source and keep browser-specific keys separated.
- Build checks scan extension sources for dangerous executable patterns and remote script URLs.
- Release packages include only the expected extension files.
- Lifecycle cleanup disconnects the main content observer and clears extension-owned intervals/timers on page unload where practical.

## Unconfirmed Concerns

- Chatto DOM selectors are fragile by nature because the extension augments a third-party page.
- Voice participant matching depends on LiveKit and Chatto behavior observed by the current implementation.
- Browser behavior has not been manually verified in this environment.

## Residual Risks

- Same-origin page scripts are not a trust boundary. A hostile Chatto page script can interact with page-world objects and observe bridge messages. The bridge is designed to keep forged messages bounded and non-privileged, but it cannot make the page world private.
- `main-world.js` remains web-accessible because it is required for fallback page-world injection in browsers that do not honor `world: "MAIN"` consistently.
- The extension stores settings by participant display name, which can collide if multiple participants share the same name.
- Local-user detection falls back to display-name matching when Chatto exposes neither a `data-local`/`data-local-participant` marker nor a stable participant id on a given card — which, per the live evidence above, is true for every card on this Chatto build today. In that fallback case, a remote participant who happens to share the local user's exact display name (after stripping trailing decoration) will also be denied a slider (verified in `test/local-card-detection.test.mjs`, "known limitation" case). This is a false negative for that one remote card, not a privacy or correctness issue for the local user, and would be resolved automatically if Chatto ever supplies a marker or id.
- `localUserName()`'s primary strategy assumes the account-panel markup keeps its current two-level nesting (name row → name span, with any status as a separate sibling subtree). If Chatto restructures that markup, resolution falls back to the older, coarser strategies, which rely on `stripTrailingDecoration()` — itself limited to stripping a *trailing* run of pictographic characters, so a prefixed or embedded decoration, or a non-pictographic decoration character, could still cause a mismatch in that fallback path.
- Chatto's LiveKit integration never attaches inbound audio `<audio>` elements to the document (`track.attach()` is called with no argument), so there is no DOM media element to key slider association off of directly; volume routing instead goes through the existing `main-world.js` bridge and participant-to-stream mapping, which is unrelated to local-user detection.
- **Unverified: the GIF-as-upload mechanism.** A chosen GIF is inserted by dispatching a synthetic `paste` `ClipboardEvent` at the composer, carrying the fetched GIF as a `File` inside a `DataTransfer` — the same technique `writeText()` already uses (successfully, confirmed live) for text, just with a `File` instead of a text string. Whether Chatto's editor treats a pasted image the way most chat apps do (upload it as an attachment) has not been confirmed against the live app; if it doesn't, `insertGif()` warns to the console (`"pasting the GIF into the composer did not seem to work"`) rather than failing silently, but does not have a second fallback mechanism. This is the one part of the feature that needs live confirmation before it can be considered working.
- **Unverified: Firefox's `background.service_worker` support.** The manifest declares an MV3 `background.service_worker`, which Firefox supports from a fairly recent version (this project's `strict_min_version` is already past that point), but this has not been confirmed against a real Firefox install. If it does not register, GIF search fails entirely on Firefox (with no other feature affected, since the background script is not used for anything else).
- **Whoever runs `npm run build` for a real release controls the Giphy key**, and must set `GIPHY_API_KEY` in their own environment (see `.env.example`) rather than committing it anywhere. There is currently no automated check preventing a future contributor from accidentally hardcoding a real key into `src/background.js` in place of the placeholder — `scripts/check.mjs`'s forbidden-filename scan guards against committing a *file* that looks like a secret, but does not scan file *contents* for an API-key-shaped string.
